# Connections — Current State

**Baseline:** Uptime `main` at `881901ab1b4d50e8afc88fde2feb50c3f5c63988`, October 22, 2026. Connections is the active Uptime gameplay experiment. It is not a migration of Packet or a declaration that Packet has been replaced. For exact behavior, inspect `Assets/Scenes/Connections.unity`, its serialized references, `Assets/Scripts/Connections/`, and `Assets/Prefabs/Connections/` on the working branch.

## Playable slice and simulation

The scene has an authored four-node, three-physical-link topology: EXT1–API, API–DB, and API–AUTH. A **logical connection** has a stable short ID and a route through that graph. Physical links and logical paths have separate view responsibilities. The scene's serialized `runMode` is **Generated**; Authored Witness mode retains c1/c2/c3 for focused review and tests.

`SimulationHost` owns one fixed-step simulation clock, active connection state, inspection history, and resolution. `ConnectionTrafficDirector` uses its own seeded random stream to queue concrete spawn plans and register arrivals through the host; queued plans can also be supplied explicitly. The default generated traffic is benign. Profiles and arrival cadence are playtest tuning, not balanced game rules. Completed or blocked generated connections leave active ownership but remain inspectable for that run. See the full [traffic document](../Design/connections-arcade-traffic-v0.md).

The current allocator grants **target-node LOAD** proportionally when requests exceed capacity after baseline LOAD. Transit nodes and physical links are route geometry in this model; they are not CPU/disk/memory/link-bandwidth allocation constraints. One allocated LOAD advances one current-operation WORK unit per second. An operation may be READ, WRITE, or EXECUTE and have its own WORK and desired LOAD. Authored multi-operation arcs advance to the next operation on the following fixed step, retaining the connection ID, route, target, and path; only final completion resolves the connection. See [LOAD](../Design/connections-arcade-load-v1.md) and [operation arcs](../Design/connections-arcade-operation-arcs-v1.md). The current arcs do not change target or route between operations.

Presentation consumes simulation state. Node LOAD bars distinguish requested from allocated LOAD; overloaded color is not a threat label. Path pulses express WRITE toward the target, READ toward origin, or EXECUTE locally, while speed/satisfaction treatments reflect allocation. The terminal has structured inspect output with an operation timeline and retains keyboard input. `inspect` can report current and retained connection history. `block <id>` resolves an active connection and releases its LOAD; `demandtest` queues a deliberate high-demand mechanical witness. Inspection and command entry are immediate; consequences progress in simulation time. [PR #8](https://github.com/abeering/uptime-game/pull/8) and the [Editor review captures](../Review/InspectOperationTimeline/README.md) record presentation work, but those captures are not Play Mode screenshots.

`ConnectionsRunRecorder` automatically starts a new JSON recording on Play start, saves the same file every 30 seconds of real elapsed time, and saves on Play stop. `mark <note>` records a bookmark with an immediate snapshot and saves; `log save`, `log dir`, and Editor-only `log folder` expose the file. Editor logs go to `<project-root>/Logs/UptimeRuns/`, which Git ignores. This is observational run evidence, **not** a game save, score ledger, replay engine, or source of random traffic. See the [recorder document](../Design/connections-run-recorder-v0.md) and its [example JSON](../Design/connections-run-recorder-example.json).

## Authority and provenance

The four current phase documents linked above retain detailed contracts and witness cases. Their older “future/deferred” lists were written at different points; where a later phase has merged, this current-state document and the final runtime/scene take precedence. In particular, the original [Connections V0 brief](../Design/connections-v0.md) is historical phase context. [Network and Connection Grammar V1](../Design/network-connection-grammar-v1.md) preserves useful conceptual distinctions but maps to an earlier CPU/disk/memory/link resource model and one-stage baseline. Those implementation claims were superseded by the LOAD, arc, traffic, and recorder merges. Do not use it as the current allocator or scene contract.

The integration history is [PR #3](https://github.com/abeering/uptime-game/pull/3) (operation identity and abstract WORK), [#4](https://github.com/abeering/uptime-game/pull/4) (LOAD), [#5](https://github.com/abeering/uptime-game/pull/5) (arcs), [#8](https://github.com/abeering/uptime-game/pull/8) (inspect), [#6](https://github.com/abeering/uptime-game/pull/6) (traffic), and [#7](https://github.com/abeering/uptime-game/pull/7) (recorder). Their descriptions and review assets explain decisions and limits; they do not override the integrated source.

## Validation and boundaries

Unity 6000.3.11f1 compiled integrated `main` and Resource, Geometry, Traffic, and Recorder Witnesses passed. These cover deterministic LOAD contention and release, stage transitions, generated plan behavior, bindings, geometry cases, and recorder output exercised by the witnesses. Interactive Play Mode review at 16:9 remains outstanding: arrivals and congestion rhythm, path/label crowding, operation transitions, `inspect` and `block`, command focus, automatic file updates, `mark`, `log save`, `log folder`, and final save on exit.

Connections V1 does not implement hostile traffic classification, infections, cleaning, company contracts, hacker campaigns, full run progression, scoring, upgrades, or network growth. Those remain relevant **Uptime-wide design directions** in [Uptime Design](../Design/Uptime_Design.md); their precise Connections mechanics are not yet established. Nor should the Packet simulation's tick, scan, or score rules be imported implicitly.
