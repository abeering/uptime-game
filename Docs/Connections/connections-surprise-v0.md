# Connections — Surprise V0 implementation

Surprise V0 is a bounded Connections implementation of shared consequence planning. Packet is unchanged. The current Duel is the first runtime consumer; the planner and executor also work without a Duel encounter. The broader Company/Villain → Run → Level → Event → concrete threats direction remains design work.

## Plan and execution contract

`ConsequencePlanner.TryPlan` resolves a plan at scheduling time. It stores the source, target, simulation time, configuration mode, effective candidate IDs, weights and eligibility reasons, seed, selection roll, selected candidate, and ordered concrete effects. Payload destinations, Worm effect and tuning, infection kind and parameter, and Condition duration are frozen in the plan. A later topology or status change can cause execution rejection; it never triggers a new roll. Worm propagation and Payload travel still use their existing seeded runtime streams after launch.

A candidate may contain one atomic effect, one or more named Tactics, inline effects, or both. A weighted candidate is one alternative, while entries in `Explicit` are performed together. `Defaults` uses the supplied table. `Additions` merges entries by case-insensitive ID and selects once across the combined table. `Custom(false, ...)` overrides matching defaults and may disable an entry with weight zero; `Custom(true, ...)` replaces the table. Negative or nonfinite weights are invalid. Ineligible weighted entries are skipped; ineligible explicit entries reject the plan. No eligible positive-weight entry rejects scheduling.

`ConsequenceExecutor.Execute` attempts each stored effect in order through the authoritative host, Worm, and Payload APIs. Each component has a success or rejection result, and successful components remain applied if another fails. A plan object can execute only once. The recorder writes `consequence_planned`, per-component `consequence_component_result`, `consequence_executed`, or `consequence_prevented`. These events carry actual launches and rejection reasons. Plans are internal evidence and are not shown to the player before resolution.

The default Duel pool has four equally weighted candidates: Phantom LOAD infection, Breach & Lockdown, Condition Worm outbreak, and Payload Burst. These weights are provisional. Breach & Lockdown attempts an existing infection and applies CLEAN LOCKED to the same node for 15 simulation seconds. An already active infection can reject while the lock still applies. The lock rejects *new* CLEAN attempts, including on an otherwise healthy node, and expires through the host's Condition lifecycle. An existing CLEAN session keeps its captured infection and may finish. The Pain stack prioritizes `CLEAN LOCKED` with remaining time; extreme stacks can exceed the authored panel's four row capacity, so lower priority Pain rows may be omitted until the stack thins.

Condition Worm outbreak starts one real Worm from the Duel target with scheduling-time SCAN JAMMED or BACKDOOR selection and copied tuning. Its traversal, node budget, branching, Conditions, and isolation counterplay are unchanged. Payload Burst selects two or three distinct reachable internal destinations where the topology permits, then starts one existing Variable Payload per destination from the Duel target. Interception, approach colors, travel, and infection delivery remain normal. A small topology may produce fewer launches; no valid destination makes the candidate ineligible.

## Duel delivery

An accepted Duel holds its plan through countdown and the race. A player win records prevention; a hacker win executes the stored plan. The one global Duel slot remains. Receipts identify the confrontation outcome and observable activity without disclosing covert infection truth. The Command Race, splash, pause option, and focus behavior are unchanged.

Advanced adds direct and carrier Duel weights of 1 each to the *existing* hostile opportunity mix (ordinary/recon/Payload/Worm/launcher are 4/2/2/1/1). The four-node scene gives both new weights zero. Direct selection chooses an internal target and requests the normal countdown. Carrier selection queues a hostile, target-aware READ connection requesting 4 LOAD and 40 WORK; completing its operation requests a Duel. Killing it beforehand prevents scheduling. Once scheduled, the Duel is independent of its carrier. Both pathways and slot rejections appear in recorder events. No separate clock is added.

The developer command `duel <node> [warningSeconds] [default|infection|breach|worm|burst|pool:...]` can force an atomic infection or named Tactic, or supply a small custom weighted table. The independent `ConsequenceWitness` calls planning and execution directly. Scene Inspector `defaultConsequencePool` can replace the built-in default table for future tuning.

## Validation and review

Run `Tools/Connections/Run Consequence Witness`, Duel Witness, and the existing Condition, Worm, Payload, Infection, Traffic, Ambient Hostile Activity, Recorder, and Advanced Scene witnesses. In Advanced Play Mode, enable generated traffic and exercise `duel API 2 breach`, `duel API 2 worm`, and `duel API 2 burst`; lose each race to inspect status, Worm movement/isolation, and red Payload approaches/interception. Try `clean API` during the lock and again after its timer. Check at 1920×1080 and 1280×720, including dense node statuses, `inspect`, command focus, and concurrent traffic. Scripted captures establish layout and state evidence; physical keyboard playtesting is a separate review step.

This slice does not add an Event graph, Level Director, progression, hacker personalities, infection-spreading Worms, generalized on-CLEAN reactions, or victory rewards. The existing Worm and Payload streams are deterministic from their own seeds, but a full run replay still depends on the same schedule and order of entity creation. The planner seed and concretized plan are recorded so that selection itself can be reconstructed independently.
