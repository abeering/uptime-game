# Connections Run Recorder V0

**Ambient Traffic Director restructure (PR #40, October 26, 2026):** Current schema-2 run metadata records `hostileGenerationEnabled`, `hostileMeanIntervalSeconds`, and the benign population controller settings in place of the old mixed-arrival interval, jitter, and hostile chance. `plan_queued.source` distinguishes `ambient_benign`, `ambient_hostile`, `spawner`, and `manual`. Each `coverage_opportunity` records the effective benign goal, occupancy, selection roll/chance, cancellation pressure, and next wait; each `hostile_opportunity` records its due time, configured mean, sampled next interval/time, chosen connection ID or skip reason. Full concrete plans and internal purpose-generation decisions remain attached to `plan_queued`. The linked JSON example below is an older version-1 recording and retains its original configuration as historical evidence.

**Lifecycle V1 update (October 25, 2026):** New recordings use schema version 2 because Blackout is now a cancellation cause rather than an outcome, and direct outage fields/events have been removed. Every materialized attempt has a `connection_spawned` event, including an offline-origin Spawner child. `connection_node_arrived` and `connection_established` record route timing. `connection_resolved` now carries its full concrete definition, attempt time, optional establishment time, resolution time, Completed/Killed/Canceled outcome, separate termination cause and phase, failure node, signed Health penalty, and resulting Health. The old `arrival_rejected` and `blackout_interruption` events are not emitted by Lifecycle V1. Network Health snapshots omit direct outage rate/count fields because infrastructure does not cause direct Health loss. See [Lifecycle V1](connections-lifecycle-v1.md).

**Infections V0 Slice 1 follow-up:** Concrete `plan_queued` and spawned operation definitions now include a typed infection payload and LOAD amount for DELIVERY. `generation.forcedOptions` records developer objective, infection type, and explicit LOAD overrides. `infection_applied`, `infection_rejected`, and `infection_removed` events preserve node, type, amount, time, reason, and source provenance. Snapshots list active infections and split node LOAD into baseline, infection, and connection request/allocation before totals. These are additive internal schema-version-1 fields; see [the infection contract](connections-infections-v0.md).

**Generation Decision Recording V0 update (October 25, 2026):** A `plan_queued` event now includes `definition`, the complete concrete plan at queue time: profile and internal intent, claim, origin, target, ordered route, every operation kind/activity/LOAD/WORK/completion effect, and full connection/operation behavior parameters. Event fields retain the connection ID, source, and scheduled spawn time. This records plans even if a run stops before arrival; `connection_spawned.definition` remains the observed spawned definition. Purpose-generated plans also include `generation.generationDecision`, distinguishing `BENIGN_NORMAL`, `BENIGN_OUTLIER`, `LOADER`, `DELIVERY_SUBTLE`, `DELIVERY_ANOMALOUS`, and `MANUAL_BENIGN`. `generation.selectedKeywords` records each selected behavior's operation index, ID, and kind; the existing anomaly IDs and normal/final values remain. A fixed manual or explicit plan has no purpose-generation trace, while its concrete queued definition is still recorded. These are additive internal fields in schema version 1. No player-facing classification is added.

**Purpose & Anomaly Generation V0 update (October 25, 2026):** The run's traffic metadata now includes six purpose-template definitions, independent mean WORK and the provisional generation rates. A generated purpose's `plan_queued` event carries internal `generation` evidence: purpose ID, objective, ordered anomaly IDs, and normal/final operation values. Older fixed profiles remain in metadata with zero default ambient weight. This is additive version-1 data for diagnosis, not player-facing classification. The historical example below predates these fields.

**Current status (October 22, 2026):** Integrated run-recording contract from [PR #7](https://github.com/abeering/uptime-game/pull/7). The example and witness results below belong to that milestone; the listed interactive Play Mode checks were not completed during integration. See [Connections Current State](Current_State.md).

**Generated Hostile Traffic V0 update (October 24, 2026):** `schemaVersion` stays at `1` because this is an additive change: older version-1 readers can ignore new fields, and existing fields keep their meanings. Each profile's recorded `ambientWeight` is the **effective** weight after Inspector overrides. Every new `NetworkSnapshot` includes `health` with `value`, signed `netRate`, `recoveryRate`, `degradationRate`, `slowedCount`, `overdueCount`, and latched `failed`, copied from the authoritative host snapshot. Counts include benign and hostile connections; degradation tracks legitimate service only. A legitimate kill emits one `health_penalty` event with `connectionId`, simulation `timeSeconds`, signed negative `healthPenaltyAmount`, and `healthAfter`, adjacent to its ordinary Killed resolution. Hostile kills emit no penalty event. The original linked example is a historical version-1 run without these additive fields; new files contain them. Illustrative excerpt (other snapshot and event fields omitted):

```json
{"snapshots":[{"timeSeconds":1,"health":{"value":99.67,"netRate":-0.33,"recoveryRate":0,"degradationRate":0.33,"slowedCount":3,"overdueCount":0,"failed":false}}],"events":[{"type":"health_penalty","timeSeconds":17,"connectionId":"a1","healthPenaltyAmount":-10,"healthAfter":75.2}]}
```

Connections records each Play Mode run automatically. The recording starts when `SimulationHost` resets at Play start, creates a JSON file immediately, saves it every 30 seconds of real elapsed time, and saves once more when Play Mode stops. Saving updates the same run file. A reset or new Play Mode session gets a new UTC timestamp and random run ID in its filename.

In the Unity Editor, find files at `<project-root>/Logs/UptimeRuns/`. The folder is created automatically and ignored by Git. Standalone builds use `Application.persistentDataPath/UptimeRuns/`. Filenames follow `uptime_YYYYMMDD_HHMMSS_seed-XXXXX_RUNID.json`, using the run's UTC start time. The output is ordinary UTF-8 JSON and can be attached directly to a ChatGPT conversation.

**Phase 3 LOADER recording (review branch):** `plan_queued.definition.loaderAttack` and `generation.loaderAttack` carry the selected structure, pattern, attack operation index, target capacity, normal and elevated LOAD, onset, spike intervals, and withdrawal duration. The complete composed operations and behavior definitions remain in the queued definition; the generation trace retains the original normal operations. Run metadata copies the provisional Traffic Director LOADER settings. The `loader_activated` event records actual activation and scheduled withdrawal from that time. A completed attacker exit emits `loader_withdrawal` and a `connection_resolved` event with outcome `Withdrawn` and cause `AttackerWithdrawal`; the resolved state remains in inspection history. Snapshots include actual activation/withdrawal times. Killed or Blackout-canceled LOADERs retain their existing outcomes and emit no later withdrawal. This is internal evidence; no player-facing threat label or recorder schema change is introduced.

## Commands

| Command | Result |
|---|---|
| `mark <note>` | Record the exact note, link it to an immediate authoritative network snapshot, and save the file. |
| `log save` | Update the run file immediately. |
| `log dir` | Print the absolute output directory. |
| `log folder` | Open that directory in Finder or the platform file manager from the Unity Editor. |

Explicit saves print the absolute file path in the Unity Console. Save errors appear in the Console and terminal; they do not stop the simulation. The recorder writes a temporary file in the same directory, then atomically replaces the previous JSON. A crash can leave the temporary file, while the last successful run file remains readable.

## Format

`schemaVersion` is currently `2` (the linked example is historical version 1). The top-level `run` object contains the unique ID, UTC start/end/save timestamps, Unity version, scene, run mode, seed, fixed step, copied node configuration, and copied ambient profile/cadence configuration. `events` has ordered sequence numbers and simulation timestamps for plan queueing, concrete connection spawns, operation starts and completions, resolution, player actions, and markers. A spawn event embeds the route and all generated operation LOAD/WORK values. Marker events carry a zero-based `snapshotIndex` into `snapshots`.

Threats V0 Slice 1 adds manual `plan_queued` events (`source: manual`), Killed resolutions and `effect` events. An infection-delivery event carries the connection ID, completed operation index, `effectType: InfectionDelivery`, `targetNodeId`, and simulation time. The operation-completed event precedes its effect, which precedes final connection resolution. Profile and concrete operation records include internal hostile classification and completion-effect settings. These are additive fields in schema version 1; the linked example predates this slice and retains its original Blocked action as a historical recording.

Slice 2's `delayed-threat` uses the same event schema. Its READ completes at index 0 without an effect; its WRITE starts on the following simulation step and completes at index 1, followed by one infection-delivery event and final resolution. A kill during WRITE retains the READ completion event and records a Killed resolution without delivery.

Slice 3A adds optional behavior definitions to recorded plan/profile metadata, effective and base WORK/LOAD in snapshots, and `modifier_added`/`modifier_removed` events with modifier ID, behavior ID, scope, associated operation index, WORK/LOAD deltas, and simulation time. The connection's runtime owns the authoritative active collection and append-only modifier history; the run recorder observes those changes. An operation-completion event records its effective required WORK and accomplished WORK, which can differ if required WORK fell below already accomplished progress.

Slice 3B records each behavior definition's kind and SPIKING normal/elevated interval durations in profile and concrete-plan metadata. Repeated SPIKING bursts use distinct modifier IDs and ordinary modifier add/remove events; OVERLOAD produces one addition and a removal at scope end. Events are timestamped when transitions are applied at a simulation-step start, including catch-up transitions after a coarse step. No recorder schema or player-facing `logs` command is added.

The Phase 2 WORK rate foundation adds each behavior's effective factor to copied definitions and modifier add/remove events, including source behavior, scope, operation index, and time. Live connection snapshots add `effectiveWorkRateMultiplier` and `actualWorkRate` alongside allocated LOAD and accomplished WORK. Older definitions resolve to neutral 1×. The recorder remains observational; these fields do not classify intent.

[`connections-run-recorder-example.json`](examples/connections-run-recorder-example.json) is the complete file saved by a Recorder Witness run. It includes a two-operation connection, a bookmark, autosave, and a blocked high-demand connection.

Snapshots are taken at about one-second **simulation** intervals after allocation, plus immediately for markers and blocks. Each contains authoritative requested and allocated LOAD for every node and current WORK, operation, demand, allocation, and performance for pending or active connections. A large manual simulation step yields one snapshot at the actual observed time; the recorder does not invent intermediate states. Autosaves use **real elapsed** time, including while simulation time is paused.

The recorder is observational. It does not consume the traffic generator's random stream, change spawn cadence, allocate LOAD, advance WORK, or affect completion. It has no log viewer, cloud upload, or gameplay analytics. Completed connection details remain in events and snapshots even after live simulation ownership retires them.

## Review

Run `Tools/Connections/Run Recorder Witness` in the Editor for schema, exact generated definitions, queued plans before spawn, explicit decisions in saved JSON, event order, snapshots, marker persistence, repeated save behavior, autosave timing seam, final save, distinct runs, and recorded/unrecorded gameplay parity. The Traffic Witness also covers all decision branches, selected keyword locations, and full queued-plan JSON round trips. Keep the Resource, Geometry, and Traffic Witnesses passing.

For visual Play Mode review, play `Connections.unity` at 16:9. Confirm a file appears immediately, its modification time advances after 30 real seconds (including with `Time.timeScale` paused), `mark test observation` persists its note and linked snapshot, `log save` updates the same file, `log dir` and `log folder` lead to the same directory, stopping Play Mode records an end time, and a second Play Mode session creates a different file. Check terminal input focus after each command. Batch Editor witnesses cannot directly confirm the Finder window or interactive Play Mode stop.
