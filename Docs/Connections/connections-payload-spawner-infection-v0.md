# Payload Spawner Infection V0

**Later integration:** [Ambient Payload Threats V0](connections-ambient-payload-threats-v0.md) lets Advanced generated INFECTORs select this existing infection. [BACKDOOR V0](connections-backdoor-v0.md) later expands connection Spawner children to Phantom LOAD, Blackout, Spawner, and BACKDOOR; Payload Spawner remains excluded.

**Scope:** Connections implementation, November 5, 2026. This is a manual playtest infection, separate from the existing connection Spawner. It does not add an ambient INFECTOR outcome or change Packet.

`infect api payload-spawner 20` installs a persistent, cleanable `PayloadSpawner` infection on API. The kind is appended after the existing infection enum values. Its Inspector-tunable default cadence is 20 simulation seconds in both Connections scenes; the development command accepts another finite positive cadence. The first attempt occurs one full cadence after application. The infection requests no LOAD and has no direct Health effect.

At each due time, the infected node selects one physically adjacent **internal** destination from the topology using a dedicated seeded random stream. Internal nodes are those outside the traffic director's configured ingress set. Candidates are sorted by node ID before the draw. A successful attempt launches one Steady Payload from the infected node to that neighbor. Because the route is one hop, the existing telegraph is red from the start of establishment. Movement, sampled 5–6-second final travel, 1.2-second establishment, 8-second interception, Phantom LOAD delivery, duplicate-infection rejection, and recorder Payload receipts remain authoritative. If there is no eligible adjacent internal destination, the attempt is skipped and recorded with `no_adjacent_internal_node`.

Payload Spawner due times bound simulation segments, so a coarse scripted step launches at the same cadence boundaries as fixed steps and continues each in-flight Payload through the rest of the step. The existing connection Spawner's scheduling and child generation remain separate. The new kind is excluded from ambient infection weights and forced `spawn ... inf:` options in V0.

The ordinary asynchronous `scan <nodeId>` reports `INFECTED` while the source instance is active. A successful PID-Select `clean <nodeId>` removes that instance and stops future launches immediately. Already launched Payloads remain independent and may still be intercepted or deliver Phantom LOAD. Launching does not automatically disclose the source to the terminal. The development `uninfect <nodeId> payload-spawner` also removes the instance.

Each `payload_spawner_attempt` recorder event includes the source infection's node, kind, application time, source connection and operation when present, cadence, chosen destination, Payload ID and profile when launched, due time, and outcome reason. Existing `payload_created`, interception, `infection_applied`, and `infection_rejected` events record the subsequent lifecycle. Repeated successful hits on a destination with active Phantom LOAD are rejected by the existing one-instance-per-kind rule; this limitation is intentional for V0.

The focused `PayloadSpawnerWitness` checks both scenes, cadence boundaries, adjacent internal targets, red presentation, interception, missed delivery, scan and PID-Select removal, in-flight independence, seeded reset/replay, coarse/fine positions, missing destinations, and recorder lineage. Existing infection, Payload, launcher, Health, CLEAN, and traffic witnesses remain regression checks. Play Mode capture results and reviewer steps are in [Payload Spawner review](../Review/ConnectionsPayloadSpawnerInfectionV0/README.md).
